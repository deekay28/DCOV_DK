# Testing the DCOV Flutter app — Windows, Android, and where Termux fits

## The one thing to get straight first

**Termux cannot build or run the Flutter app.** Building a Flutter app for
Android needs the Android SDK, NDK, Gradle, and a JDK — a full toolchain that
assumes a desktop OS underneath it. Termux gives you a Linux userland on the
phone, not that toolchain, and there's no supported way to install one there.

Termux's job in this project is exactly what it was in the last two
messages: **running the backend API** on the phone. The Flutter app is a
*separate* thing, built on a real desktop machine and then either installed
on the phone as an APK or run natively as a Windows app.

So the actual shape of testing is:

| Task | Machine | Tool |
|---|---|---|
| Build the app | Windows (or macOS/Linux) | Flutter SDK |
| Run/test on Windows | same Windows machine | `flutter run -d windows` |
| Run/test on Android | Windows machine + a phone (USB) or an emulator | `flutter run -d <device>` |
| Run/test on iPhone | **needs a Mac** — Windows cannot do this at all | Xcode |
| Host the backend for the app to talk to | Windows, or the phone via Termux, or Docker | see `docs/DEPLOY.md` / `docs/TERMUX.md` |

Termux only ever appears in the bottom row, as one option for where the
backend lives — never as a place the Flutter app itself runs or builds.

## Recommended setup: develop and test from Windows

This is the right primary platform for you, since it's the one machine that
can reach three of your four targets (Windows desktop, Android device,
Android emulator) directly, and Flutter's tooling on Windows is solid.

### 1. Install the toolchain (one-time)

1. Install [Flutter SDK](https://docs.flutter.dev/get-started/install/windows)
   — unzip, add `flutter\bin` to PATH.
2. Install [Android Studio](https://developer.android.com/studio) — this is
   what actually gets you the Android SDK, platform tools (`adb`), and an
   emulator manager, even if you never open its editor.
3. Run `flutter doctor` in a terminal and fix whatever it flags red —
   usually "Android licenses not accepted" (`flutter doctor --android-licenses`)
   or a missing Visual Studio C++ workload (needed for Windows desktop builds:
   Android Studio installer offers it, or grab "Desktop development with C++"
   from the Visual Studio Installer).
4. Confirm: `flutter doctor -v` should show checkmarks for Windows, Android
   toolchain, and Android Studio at minimum.

### 2. Get the project ready

**Important correction to what I told you before:** this repo ships only
`lib/`, `test/`, `assets/`, and `pubspec.yaml` — the source code. It does
*not* ship `android/`, `ios/`, `windows/`, `macos/`, `linux/`, or `web/` —
the actual Gradle project, Xcode project, and platform manifests that
`flutter build` needs. Those are generated by the Flutter SDK itself
(`flutter create` uses templates bundled with your installed SDK version),
which means they genuinely cannot be produced in the sandbox I wrote this
code in — there's no Flutter SDK there, and no network to fetch one. This
isn't a build step I skipped; it's a build step that can only happen on a
machine that has the SDK, which from here means yours.

```powershell
cd frontend_flutter
flutter create .            # generates android/, ios/, windows/, etc. IN PLACE
                             # - it will not touch lib/, test/, or pubspec.yaml,
                             # only add the platform folders that are missing
flutter pub get
```

`flutter pub get` alone (what I said before this correction) will fail or
silently produce a project you can't actually build — `flutter create .`
first is the real first step.

#### Then: add the permissions `flutter create` doesn't know you need

The generated Android/iOS projects are bare — they don't know this app uses
the camera (`mobile_scanner`, `image_picker`) or vibration
(`vibration`). Add these before your first `flutter run`, or the
barcode/QR scan and chip-photo buttons will crash or silently fail on a
real device:

**`android/app/src/main/AndroidManifest.xml`** — inside the `<manifest>`
tag, before `<application>`:
```xml
<uses-permission android:name="android.permission.CAMERA" />
<uses-permission android:name="android.permission.VIBRATE" />
<uses-feature android:name="android.hardware.camera" android:required="false" />
```
(`android:required="false"` so the app still installs on a device/emulator
with no camera — barcode scanning just won't work there, which is correct.)

**`ios/Runner/Info.plist`** — inside the outermost `<dict>`:
```xml
<key>NSCameraUsageDescription</key>
<string>DCOV uses the camera to scan barcodes/QR codes and photograph component markings.</string>
<key>NSPhotoLibraryUsageDescription</key>
<string>DCOV needs photo library access to attach a component photo when the camera isn't available.</string>
```

Windows/macOS/Linux desktop builds need no equivalent permission
declarations for what this app does.

This is also the fastest sanity check that nothing in `lib/` is
structurally broken — if a dependency or import is wrong, `flutter pub get`
is where you'd see it, before ever touching a device.

### 3. Run the matching-engine tests

```powershell
flutter test
```

This runs `test/matching_test.dart`, which checks the Dart port of the
matching cascade against the same vectors I checked the Python and
JavaScript versions against — an OCR misread, a lot-code suffix, a
double-glyph substitution, a clean hit, and a genuine miss. This test needs
no device, no emulator, and no backend — it's the quickest thing to run
after any change to `lib/services/matching.dart`.

### 4. Fastest UI loop: Chrome

```powershell
flutter run -d chrome
```

Not one of your four target platforms, but by far the fastest edit-reload
cycle for UI work — hot reload is near-instant in Chrome. Use it to iterate
on layout and flow, then confirm on a real target before calling something
done. Barcode scanning and camera capture behave differently in a browser
(permission prompts, no native camera UI), so don't treat a Chrome pass as
sufficient for the scan flow specifically.

### 5. Windows desktop

```powershell
flutter run -d windows
```

Builds and launches a native `.exe`. This is a first-class target — test the
full flow here, including `image_picker`'s file-dialog fallback (Windows has
no "camera capture" concept the way a phone does; the app already falls back
to picking an image file when camera capture isn't available — see the
try/catch in `lib/screens/verify_screen.dart`).

For a distributable build: `flutter build windows` — output lands in
`build\windows\x64\runner\Release\`.

### 6. Android — real device (recommended over the emulator for scanning)

Barcode/QR scanning and the camera-capture flow need a real camera, so a
physical phone is worth the two minutes of setup over the emulator whenever
you're testing that path specifically.

1. On the phone: Settings → About phone → tap "Build number" 7 times to
   unlock Developer Options → enable **USB debugging**.
2. Plug the phone into the Windows machine via USB, accept the "Allow USB
   debugging" prompt on the phone.
3. Confirm it's visible:
   ```powershell
   flutter devices
   ```
   You should see the phone listed with a device id.
4. ```powershell
   flutter run -d <device-id>
   ```
   Hot reload works the same as on desktop/Chrome.

For a build you can hand to someone else or sideload without a USB cable:
```powershell
flutter build apk --release
# output: build\app\outputs\flutter-apk\app-release.apk
```
Copy that file to the phone (email, cloud drive, `adb push`) and open it —
Android will prompt to allow installing from that source.

**One thing worth knowing about that release APK before you hand it to
anyone:** without a signing config, `flutter build apk --release` signs it
with Flutter's *debug* keystore — it installs and runs fine for testing, but
it's not what you'd distribute as "the real app." For that you'd generate
your own upload key (`keytool -genkey -v -keystore ~/dcov-release-key.jks
-keyalg RSA -keysize 2048 -validity 10000 -alias dcov`) and point
`android/app/build.gradle`'s `signingConfigs` at it — the [official Flutter
docs on signing](https://docs.flutter.dev/deployment/android#signing-the-app)
cover this in about five minutes. Fine to skip for internal testing; do it
before this goes to anyone outside your immediate team.

### 7. Android — emulator (fine for everything except the actual scan)

In Android Studio: Tools → Device Manager → Create Device → pick a Pixel
profile with a recent API level → launch it. Then:
```powershell
flutter devices        # confirm the emulator shows up
flutter run -d emulator-5554
```
The emulator's virtual camera shows a test pattern, not a real chip package,
so use it for everything *except* validating the scan/OCR flow — navigation,
catalogue search, the offline matching engine, the dashboard, all work
identically to a real device.

### 8. iPhone — you need a Mac

Windows cannot build or sign an iOS app; there's no workaround, this is an
Apple platform restriction, not a Flutter limitation. Options, roughly
cheapest to most involved:

- Borrow/use any Mac with Xcode installed — `flutter run -d <iphone>` there
  works exactly like the Android flow above once you've set up a free Apple
  ID for local device testing (App Store distribution needs a paid Apple
  Developer account; installing on your own device for testing does not).
- A cloud Mac CI service (Codemagic, GitHub Actions `macos-latest` runners,
  MacStadium) if you want iOS builds without owning Mac hardware.
- This is worth doing before shipping to real iPhone-carrying inspectors,
  but not before the Android/Windows paths are solid — the app code itself
  is already cross-platform; nothing in `lib/` is Android-specific.

## Pointing the app at a backend

Wherever the backend runs (Windows via `quickstart_local.sh`/Docker, or a
phone via Termux — see `docs/DEPLOY.md` and `docs/TERMUX.md`), the Flutter
app needs that machine's **network address**, not `localhost` — the app and
the backend are on different devices unless you're running both on the same
Windows machine.

- Backend on the same Windows PC you're running `flutter run -d windows`
  from: `http://127.0.0.1:8000` works fine.
- Backend on your Windows PC, app running on a phone (USB or Wi-Fi):
  use the PC's LAN IP, e.g. `http://192.168.1.20:8000` — find it with
  `ipconfig` on Windows, look for the Wi-Fi adapter's IPv4 address. Make
  sure Windows Firewall isn't blocking inbound connections on port 8000
  (it'll usually prompt the first time; allow it for private networks).
- Backend on the phone itself via Termux, app also on that same phone:
  `http://127.0.0.1:8000` again, since they're the same device.
- Backend on the phone via Termux, app on a *different* device: find the
  phone's IP with `ip addr` inside Termux, use that.

Enter the address on the login screen under "Change server address" before
signing in. Until you sign in, the app works fully offline against the
203-record catalogue bundled at build time (`assets/data/components_seed.json`)
— that's deliberate, so a fresh install is useful in the field before it's
ever been near a server.

## What to actually check once it's running

Same four verdicts as the web demo, now through the native scan flow instead
of typed samples:

1. **Manual entry** — type `STM32F302C8T6` on the Verify tab, confirm RED
   with the full cascade trace.
2. **Barcode/QR** — tap "Scan code", point it at any barcode (even an
   unrelated product barcode off a box works to confirm the scanner itself
   functions; it'll correctly come back GREY/not-found since it's not in
   the catalogue).
3. **Chip photo** — tap "Photograph chip", take or pick any photo. Offline,
   it goes straight to manual entry with the photo shown for reference;
   online, it calls the server OCR endpoint if `INSTALL_VISION=true` was
   set when you built the backend image (see `docs/DEPLOY.md` — otherwise
   you'll get a clear "server OCR unavailable" message, not a silent
   failure).
4. **Catalogue tab** — filter by Origin → Chinese, Criticality → Critical;
   should match the 29 shown on Overview.
5. **History tab** — confirms scans are being recorded locally, and (once
   signed in) shows a pending-sync count if you scan while offline and
   haven't reconnected yet.
6. **Theme toggle** (top-right icon) — dark/light, same palette as the web
   demo.
7. **PIN unlock** — sign in with a password, go to Settings → Security, set
   up a PIN. Sign out, reopen the login screen: it should default to the PIN
   form for that username. Confirm the PIN actually unlocks. Then — this is
   the check that matters — try the *same* PIN from a second device (or a
   fresh install/emulator instance) against the same account: it must be
   rejected, since that device never completed a password login. If it's
   ever accepted from an unrecognized device, that's a serious regression,
   not a cosmetic bug — file it immediately.

If a scan's verdict here ever disagrees with the same marking on the
offline web demo or via `scripts/smoke_test.sh` against the backend, that's
a real bug — the three matching engines are supposed to be provably
identical (see `test/matching_test.dart`'s header comment); file it as a
Dart-port bug specifically, since Python and JS are the reference.
